1 The big picture

The whole quality-control desk runs today on Google Forms + Sheets. The goal is to run it from VOW, make the standards (machine lists, qualities, std weights/MR%/CV bands) configurable, and link every input to an existing VOW master. There are ~28 reports across the mill process flow. They cluster into a handful of families that each share one shape — so building the first report of a family creates a reusable pattern for the rest.

4 New storage (minimal — YAGNI)

Entry table — NEW

jute_sqc_spreader_roll_wt
  • Morrah-shaped: header keys + JSON readings (10 wt + 10 MR%)
  • persisted calc_* (avg, corrected, StDev, CV%) + band counts
  • standard tail: co_id, branch_id, entry_date, active, updated_by, updated_date_time

Standards satellite — NEW

jute_spreader_quality_attr
  • item_id-keyed (mirrors jute_yarn_mst) — holds std_mr_pct
  • keeps item_mst clean — no SQC columns on the core item master
  • seed real per-quality values later; code falls back to base 16

Reuse existing — ALTER

spreader_machine_attr
  • std roll weight (wt_per_roll) already lives here & is already queried
  • add 5 nullable band-edge columns (Spreader-2 uses the 85–105 set)
  • helper defaults to the 55–75 bands when unset

Standards rule

Per the owner's direction, a quality's standards live in an item_id-keyed satellite — never as columns on item_mst, and never one giant composite standards table. Reuse a satellite where one fits, create a stage one where none exists.

5 Production linkage — independent vs Phase 2

This report is essentially independent of production transactions — every input is either a master pull or a fresh bench reading, so it's fully buildable now (Phase 1). The only production-coupled items are correctly deferred:

Independent now

  • date, feeder, the 10 roll weights, the 10 MR% — typed at the bench
  • spell / machine / quality — pure existing-master pulls
  • std MR% & band edges — standards, not transactions

Phase 2 (deferred)

  • feeder as an HRMS employee (vs free text)
  • "rolls actually made" pulled from the spreader production run for that machine/date/spell
  • Neither is needed to compute the QC stats — that's exactly why Family-A is the right Phase-1 start.

Backend & frontend build in parallel (separate repos). Nothing is committed by the agents — the orchestrator reviews the pytest result and the adversarial review verdict, fixes any blockers, then commits & pushes both repos to claude/keen-keller-fw2r1z. Migrations are generated as SQL only — the live dev3 DB is unreachable from the build sandbox, so they're applied later where dev3 is reachable.
